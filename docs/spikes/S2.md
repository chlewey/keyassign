# S2. Reading the layout in use

Requirement R4.1 (and M3's "load the layout in use"). Question: can Key Assign read
an installed layout's tables, including dead keys and ligatures, without changing
anything and without reverse-engineering the layout DLL?

**Answer: yes, by probing.** Ask Windows what each key types with `ToUnicodeEx`
instead of parsing the DLL. It needs no administrator rights, changes nothing, and
read all 218 layouts Windows ships in about 3 seconds in total.

The proof of concept is `spikes/S2.ReadLayout/`. It is throwaway code that
shows the method; M3 will rebuild it properly in Core behind an interface.

## Method

1. Take the layout's `HKL`: from `GetKeyboardLayoutList` for the layouts in the
   user's input list, or from `LoadKeyboardLayout(klid, KLF_NOTELLSHELL)` for any
   layout under `HKLM\SYSTEM\CurrentControlSet\Control\Keyboard Layouts`.
   `KLF_NOTELLSHELL` without `KLF_ACTIVATE` loads it into this process only. It
   does not touch the input list or the registry. `UnloadKeyboardLayout` undoes it.
2. For each scan code in the main block (plus the ISO, ABNT and JIS extra keys),
   turn it into a virtual key with `MapVirtualKeyEx(…, MAPVK_VSC_TO_VK_EX, hkl)`.
3. Call `ToUnicodeEx` four times with a hand-built key state for Normal, Shift,
   AltGr (Ctrl+Alt) and AltGr+Shift. A positive result is the text, up to several
   UTF-16 units (a ligature). A negative one is a dead key, and the buffer holds its
   accent.
4. Caps Lock: repeat Normal and AltGr with the Caps Lock toggle bit set, and
   compare with Shift and AltGr+Shift. That gives each key's `CapsBehavior`.
5. Dead key tables: press the dead key, then every key that types one character,
   and keep the pairs whose result is a different single character. Two characters
   (accent plus base) means no composition.
6. After each dead key, flush by sending a space with no modifiers, or the pending
   state leaks into the next probe. Do not pass the "don't change keyboard state"
   flag: it also stops dead keys from working.

## Results

Run over every layout in the registry on Windows 11 (build 26200):

| | |
|---|---|
| Layouts loaded and probed | 218 of 218 |
| Written in the text format and parsed back to an equal model | 218 of 218 |
| Layouts with dead keys | 92 |
| Largest dead key set | German Extended (E1): 20 dead keys, 764 entries |
| Layouts with multi-character keys (ligatures) | 54, none over 4 UTF-16 units |
| Time | 7 to 97 ms per layout, 2.9 s for all |

Spot checks against known layouts: Spanish has dead `´` on its `'` key, and `´` + `a`
gives `á`; `~` accepts only `a n o` and their capitals; US types `a`/`A` and has
no dead keys; US-International has the expected five. The files in
`spikes/S2.ReadLayout/samples/` are the output for Spanish, Czech, Devanagari
(ligatures) and BÉPO.

Checking a layout against Microsoft's `kbd.h` tables was not done: the probe agrees
with what Windows types, which is what the user sees, and no layout DLL source was
needed.

## What the model cannot say yet

These are the gaps the probe found. None blocks reading; each needs a decision
before M3 shows or M5 writes such a layout.

1. **Chained dead keys (R3.5).** Four layouts have dead keys whose result is another
   dead key: German Extended (E1, E2), BÉPO and Cherokee Phonetic. The model's dead
   tables map a base to one character, so the probe notes these and skips them.
   Whether Windows 11 apps accept chains at all is spike S5. Reading them is
   also harder: after dead + dead, `ToUnicodeEx`
   returns a dead result whose character is not the new accent (it showed as a
   space), so a chain cannot be named from one call.
2. **Caps Lock giving a third value.** In 24 layouts Caps Lock does not just
   swap Shift. On Czech's digit row, Normal types `ě` and Shift types `2`, and Caps
   Lock gives the capital `Ě`, a third value. Cherokee and Hebrew are also among
   the 24, for reasons not yet looked at. `CapsBehavior` has three values and the probe falls back
   to the closest, counting the key as unrepresentable. Either the model grows
   (an explicit output for Caps Lock, as Windows does with `SGCAPS`) or those keys
   are read with a warning. Windows can also make Caps Lock affect AltGr alone.
3. **Keys not read.** Keypad and other extended keys (the `E0` prefix) and the
   Ctrl levels are not probed, and outputs that are control characters are dropped. Only the main block and the ISO, ABNT and JIS extra keys are.
4. **Names.** `Layout Text` in the registry gives the layout name. A few user
   input-list entries carry an `HKL` with no matching registry key, and the probe
   falls back to the code. M3 should show the display name Windows shows.
5. **IME layouts** (Chinese, Japanese, Korean) type through an input method, not
   through the layout's tables. Probing them gives only what the base layout does.

## Findings for the plan

- **R4.1 holds with no reverse engineering.** The kbd.h-parsing fallback in
  `docs/MVP.md` is not needed. Keep it as a note, not a task.
- **M3 can start** from this method. It needs an `ILayoutReader` over the user32
  calls, a fake for tests (tests never touch the real system), and the caps and chain
  gaps above decided first.
- The result is what Windows types now, not the DLL. Editing and installing (M5)
  still needs a model that can be compiled back to tables, so the gaps above are
  also M5 gaps.
- Nothing in S2 installs or changes a layout, so it ran on the main machine. S3
  and S5 do install layouts and need the throwaway VM.
