# S1. Building the DLL

Requirement R4.2. Question: generate the layout DLL directly (it is mostly data
tables), or rely on Microsoft's MSKLC, whose redistribution terms and ARM64 support
need checking? Does Windows require the DLL to be signed?

**Answer so far: generate it directly.** A layout DLL is a small PE file with one
export and a table of data, and Key Assign can write it with no compiler, no
`kbdutool` and no MSKLC. This spike proves that the file is a valid image that
Windows loads and that its tables read back as the model. It does **not** prove that
Windows accepts it as a keyboard: that needs installing, which is S3 on the VM.

The proof of concept is `spikes/S1.BuildDll/` (x64 only, throwaway). M5 will rebuild
it in Core.

## What was checked

| Check | Result |
|---|---|
| Walk Windows' own `kbdus.dll` with my reading of `kbd.h`'s `KBDTABLES` (x64 offsets) | Reads as expected: three modifier bits, 127 scan codes, version 1 in the high word of `fLocaleFlags` |
| Write those tables back out as a new DLL, `LoadLibrary` it, call `KbdLayerDescriptor`, read again | Tables identical |
| Layout model, to tables, to DLL, to loaded tables, back to the model, for the 3 samples and the 218 layouts S2 probed | 221 of 221 round-trip exactly |
| Decode Windows' own 218 layout DLLs and compare with what `ToUnicodeEx` reported in S2 | 201 identical; the other 17 are explained below |
| Size and speed | 5 to 10 KB per DLL, a few milliseconds to build |

The headers copy kbdus.dll's: DLL, x64, native subsystem, no entry point, image base
`0x180000000`, `DYNAMIC_BASE`, one export (`KbdLayerDescriptor`, code
`lea rax,[rip+disp]; ret`), base relocations for the table pointers. The timestamp is
zero, so the same layout gives the same bytes.

## How a layout becomes tables

- Modifier bits Shift=1, Ctrl=2, Alt=4. Columns: Normal, Shift, Ctrl, AltGr (Ctrl+Alt),
  AltGr+Shift. Ctrl holds control characters for letters and brackets, nothing else.
- Each key needs its own virtual key (VK), because the character table is keyed by VK.
  Latin letters get their letter's VK; other keys keep the US position's VK; keys
  displaced by a letter (Dvorak, AZERTY) get an unused OEM or digit VK. 17 of the 221
  layouts needed that, and the shortcuts that follow a VK (Ctrl+letter) follow the
  letter, as in real layouts.
- A dead key is `WCH_DEAD` in its row plus a `VK__none_` row holding the accent. The
  tables list `(base, accent, result)` rows. Ligatures are `WCH_LGTR` plus a ligature
  table, padded to the longest with `WCH_NONE`.
- `CapsBehavior` maps to `CAPLOK` and `CAPLOKALTGR`. `KLLF_ALTGR` is set when any key
  has an AltGr output.
- What the model does not own comes from a template: Tab, Enter, the keypad, function
  keys, key names, the `E0` and `E1` tables. The spike reads `kbdus.dll` for them; the
  product should embed them as constants.

## Findings

1. **No MSKLC needed, so its terms do not matter.** Direct generation avoids the
   redistribution question and the ARM64 gap (MSKLC itself builds only x86, x64 and
   the retired IA-64; ARM64 needs the WDK, or the `kbdutool -u` ARM64EC route some
   forum answers describe). These come from search results and forum posts, not from
   the MSKLC licence, which I could not find; D2 should not rest on them.
2. **Reading the DLL is also possible, and it is more complete than probing.** The
   same reader decodes any layout DLL. Against S2's probe it shows what probing cannot
   see: dead key entries the probe did not find (Tibetan `M` and `m`, French BÉPO),
   whole dead keys it never reached (Canadian Multilingual's `¯`, German Extended's
   `1`), and Caps Lock attributes on keys whose Normal and Shift outputs match. I
   did not look into why each differs, so these are leads. If Key Assign reads the
   DLL where it can and falls back to probing, it would close S2's chained-dead-key
   gap for reading.
3. **Real DLLs repeat dead key entries.** One shipped layout's `´` table lists `N` twice
   (found when decoding, layout not recorded). The
   model rejects duplicates, so the reader keeps the first. Which one Windows uses is
   a question for S3.
4. **The format has a place for what the model lacks.** `DKF_DEAD` chains dead keys
   (S5), and `SGCAPS` gives Caps Lock its own output (decision D5). Both are in the
   file format; the spike's builder does not write them yet.
5. **One scan code, two keys.** JIS (`7D`) and ABNT (`73`) keys map to a VK another
   key already owns in real DLLs. The model keys by scan code and the tables by VK, so
   M5 must decide which key owns the VK.

## Not settled, and who settles it

- **Signing.** Nothing I read says a custom layout DLL must be signed, and
  winkbdlayouts' README (BSD-2, builds x86, x64 and ARM64 from C with the SDK's
  `kbd.h`) just copies the DLL to `System32`. "Not mentioned" is not "not required".
  S3 on the VM decides it: install an unsigned DLL and try to select it.
- **Registration.** The same README gives the registry entry:
  `HKLM\SYSTEM\CurrentControlSet\Control\Keyboard Layouts\<KLID>` with `Layout File`,
  `Layout Text` and `Layout Id`. It says that without `Layout Id` the layout shows in
  Settings but is never activated, and that the high four digits of the KLID must be
  unique. Whether sign-out is needed is for S3.
- **ARM64 and x86.** Not built. ARM64 uses the same table layout as x64 (8-byte
  pointers), with a different machine type and stub. x86 has 4-byte pointers, so every
  structure changes size. Untested. Whether a 32-bit app on x64 needs a SysWOW64 copy
  is also for S3.
- **Names.** The spike reuses US key names. `GetKeyNameText` for the keys of other
  scripts, and the layout's display name in the language bar, are for S3.

## Running it

```
dotnet run --project spikes/S1.BuildDll -- reemit
dotnet run --project spikes/S1.BuildDll -- roundtrip tests/KeyAssign.Core.Tests/Samples
dotnet run --project spikes/S1.BuildDll -- compare-system <folder with S2's .kal files>
dotnet run --project spikes/S1.BuildDll -- dump C:\Windows\System32\kbdus.dll
```

Output DLLs go to `%TEMP%\keyassign-s1`. They are loaded into the process only, never
registered, installed or copied to a system folder.
